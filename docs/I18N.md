# Lokalisierung (i18n)

Stand: 2026-10-16. Die Oberfläche ist in **sechs Sprachen** verfügbar: Englisch (`en`, Quellsprache), Deutsch (`de`), Spanisch (`es`), Französisch (`fr`), Italienisch (`it`) und vereinfachtes Chinesisch (`zh`).

## So funktioniert es

| Teil | Ort |
|---|---|
| Setup (Sprachen, Namespaces, `<html lang>`) | `client/src/lib/i18n.ts` |
| Texte | `client/public/locales/<sprache>/<namespace>.json` |
| Namespaces | `translation` (fast alles), `tickets`, `analytics`, `modPerf`, `server` (Fehlermeldungen der API) |
| Datum in der UI-Sprache | `client/src/lib/date-locale.ts` → `useDateLocale()` |
| Server-Fehlermeldungen übersetzen | `client/src/lib/server-messages.ts` |
| Sprachauswahl | `client/src/components/theme/language-toggle.tsx` |

**Text im Code:** immer über `t()` und immer mit englischem Standardtext:

```tsx
const { t } = useTranslation();
t("theme_builder.save", "Save theme");
t("x.count", { count, defaultValue: "{{count}} items" });
```

Texte in Konstanten (Listen, Menüs) bekommen einen Schlüssel und einen Fallback und werden beim Rendern übersetzt: `{ labelKey: "admin_bulk.toolbar.ban", fallback: "Ban selected" }` → `t(item.labelKey, item.fallback)`.

**Datum:** `format(date, "PPP", { locale: dateLocale })` bzw. `formatDistanceToNow(date, { addSuffix: true, locale: dateLocale })` mit `const dateLocale = useDateLocale();`. Reine Zahlenformate (`HH:mm`, `yyyy-MM-dd`) brauchen kein `locale`.

**Fehlermeldungen der API:** Der Server antwortet immer auf **Englisch** (`res.status(400).send("Username already taken")` oder `.json({ error: "…" })`). `en/server.json` ordnet jedem dieser Texte einen Schlüssel zu, der Client zeigt die Übersetzung an (`ApiError.message`). Neue Servermeldung → Eintrag in `en/server.json` plus Übersetzungen, sonst schlägt der Test fehl.

**Neuer Text, Schritt für Schritt**
1. Im Code `t("bereich.schluessel", "English text")` verwenden.
2. Den Schlüssel mit dem identischen englischen Text in `en/<namespace>.json` eintragen.
3. Den Schlüssel in `de`, `es`, `fr`, `it`, `zh` übersetzen (Platzhalter wie `{{name}}` unverändert lassen).
4. `npm run test:i18n` ausführen.

**Stil je Sprache:** Deutsch „du“; Spanisch „tú“; Französisch „tu“ mit geschütztem Leerzeichen vor `? ! : ;`; Italienisch „tu“; Chinesisch „你“ mit Vollbreiten-Satzzeichen. Feste Begriffe, z. B. Deutsch: Beitrag, Kommentar, Community, sperren/Sperre, Meldung, Inhaber, Benutzer, Ticket, Theme.

## Tests (`npm run test:i18n`)

`tests/i18n/i18n.test.ts`, Analyse in `tests/i18n/scan.ts` (TypeScript-AST, kein Regex-Raten). Geprüft wird:

- **Kein fest einprogrammierter Text** in `client/src`: JSX-Text, Attribute wie `placeholder`/`title`/`alt`/`aria-label`, `toast({ title, description })`, `confirm()`/`alert()`, Strings in Bedingungen im JSX, einzelne Wörter wie „Save“. Ausnahmen mit Begründung in `tests/i18n/allowlist.json` (Markenname, Sternbildnamen, Sprachnamen).
- **Jeder im Code verwendete Schlüssel existiert** auf Englisch (auch dynamische Präfixe wie `` t(`status.${s}`) `` und Schlüssel in Datenobjekten).
- **Standardtext im Code = englischer Text** in der Sprachdatei (kein deutscher oder abweichender Fallback), und kein Schlüssel mit zwei verschiedenen Standardtexten.
- **Datumsangaben mit Monats-/Tagesnamen** übergeben die UI-Sprache an date-fns.
- **Jede Fehlermeldung des Servers** hat einen Eintrag im Namespace `server` und ist englisch.
- **Jede Sprache** hat jede Datei und jeden Schlüssel, keine Extra- oder leeren Einträge, identische `{{Platzhalter}}`, und keine unübersetzten englischen Sätze (geprüfte Ausnahmen in der Allowlist).
- **Sprachauswahl** und `supportedLngs` stimmen überein.

Direkt anzeigen, welche Texte noch fest im Code stehen: `npx tsx tests/i18n/scan.ts`.

## Audit 2026-10-16

### Ausgangslage
- **Fest im Code:** rund 450 Texte standen fest im Code, überwiegend Englisch, vereinzelt Deutsch, etwa die Willkommensmeldung oder „… ungelesen“.
- **Fehlende Schlüssel:** 366 im Code verwendete Schlüssel fehlten in den Sprachdateien. Angezeigt wurde nur der Fallback im Code, in jeder Sprache gleich.
- **Lücken in den Sprachen:** In `es`/`fr`/`it`/`zh` fehlten je 271 Schlüssel von `translation`. `tickets` war in diesen Sprachen komplett Englisch, `modPerf` fehlte ganz.
- **Analytics und Moderator-Leistung:** Beide Seiten luden ihre Namespaces nie und waren deshalb immer Englisch.
- **Datum:** Datumsangaben waren immer Englisch, das Beitragsalter dagegen immer Deutsch.
- **Servermeldungen:** Fehlermeldungen erschienen roh als `400: {"error":"…"}`, gemischt Englisch und Deutsch.
- **Ticket-Systemmeldungen und Log-Aktionen:** „Ticket created“ und Status-Wechsel kamen als englischer Text aus der Datenbank. Log-Aktionen standen als Code da, z. B. `auth.login`.
- **Deutsch:** gemischt „Sie“ und „du“, „bannen“ und „sperren“, „Owner“, „Report“, „...“.

### Ergebnis
- **0** fest einprogrammierte Texte (Scanner über alle 152 Quelldateien in `client/src`).
- **1654 Einträge je Sprache** (`translation` 1242, `tickets` 160, `analytics` 35, `modPerf` 41, `server` 176), in allen sechs Sprachen vollständig. Platzhalter sind geprüft.
- **Bestehende Übersetzungen überarbeitet:** Deutsch 171, Spanisch 257, Französisch 291, Italienisch 218, Chinesisch 148 Korrekturen. Behoben wurden falsche Bedeutungen (z. B. Spanisch „Lata“, also „Dose“, für „Poster“), Anrede, Begriffe, Typografie und unvollständige Sätze.
- **Datum, Log-Aktionen, Ticket-Systemmeldungen und API-Fehlermeldungen** erscheinen jetzt in der UI-Sprache. `<html lang>` folgt der Sprache.
- **Browser-Audit:** Jede Seite (34 Routen, alle Tabs, als Inhaber, dazu die Anmeldeseite als Gast) wurde in allen sechs Sprachen geprüft. Ergebnis: siehe Abschnitt „Prüfläufe“.

### Bewusst nicht übersetzt
- **Inhalte von Nutzern** (Beiträge, Namen, Community-Namen, Ticket-Texte).
- **Markenname** Osiris / Open-Verse / „Verse“, **Sprachnamen** im Sprachmenü (Endonyme) und **Sternbildnamen** im Dekor (offizielle IAU-Namen).
- **Technische Codes** in Code-Elementen und Tooltips (z. B. Log-Aktionscode `auth.login`, „USER::{{id}}“ im Sperren-Bereich), WCAG-Stufen „AA/AAA“.

### Offene Punkte / Empfehlungen
- **Formulierte Servermeldungen mit Variablen** (z. B. Texte mit `${…}`) und Zod-Validierungsfehler der API werden nicht erkannt und erscheinen auf Englisch. Besser wäre ein `code` in jeder Fehlerantwort, den der Client übersetzt.
- **Neue Sprachen** brauchen einen Ordner unter `client/public/locales/`, einen Eintrag in `supportedLngs` und in der Sprachauswahl sowie eine date-fns-Locale in `date-locale.ts`. Den Rest prüfen die Tests.
- **Zahlen** (`toLocaleString()`) richten sich nach der Browser-Sprache, nicht nach der UI-Sprache. Das ist meist identisch und bewusst so gelassen.
